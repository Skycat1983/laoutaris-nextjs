# A-010 Performance, SEO, And Accessibility Result

Status: Completed

Audit goal: [A-010 Performance, SEO, and accessibility](../goals.md#a-010-performance-seo-and-accessibility)

Workstream: [Frontend routes and components](../../workstreams/frontend-routes-and-components.md)

## Summary

Public route performance, SEO, and accessibility need production hardening before
launch. The highest-impact issues are that all public routes currently build as
dynamic server-rendered routes, the root metadata is still the scaffolded Create
Next App copy, discovery files are absent, and several public header/search
controls are not semantic keyboard-accessible controls.

The build and lint baseline is clean, so these findings are not covered by the
current automated checks. Reconciliation should prioritize the public route
rendering/cache boundary, route metadata/discovery output, and public navigation
accessibility before visual polish.

## Findings

### A010-F01: Public routes are dynamic and perform auth/database work on every request

Severity: High

Evidence:

- `src/app/layout.tsx` exports only root metadata and calls `dbConnect()` plus
  `getServerSession(authOptions)` before rendering every route.
- `src/middleware.ts` calls `getToken()` before checking `isProtectedRoute(path)`,
  so token parsing runs for public routes as well as protected routes.
- `npm run build` completed successfully, but every listed public route was
  marked dynamic, including `/`, `/artwork`, `/artwork/[artworkId]`,
  `/blog`, `/blog/[slug]`, `/search`, `/shop/products`, and
  `/shop/products/[productHandle]`.
- The same build output reported middleware size at 48 kB.

Impact: public archive and shop pages cannot benefit from static generation or
ISR while this root/session/middleware pattern remains global. This increases
TTFB risk, makes public SEO crawls dependent on request-time MongoDB/auth
availability, and reduces cacheability for high-value archive, artwork, blog,
and product pages.

Candidate follow-up: split public and authenticated layouts or make session
hydration route-scoped; move middleware token parsing behind the protected-route
check; then define static/ISR/cache strategy for public archive, blog, and shop
routes.

### A010-F02: Production metadata and crawl discovery are missing

Severity: High

Evidence:

- `src/app/layout.tsx` still sets `title: "Create Next App"` and
  `description: "Generated by create next app"`.
- `rg` found no route-level `generateMetadata`, `openGraph`, `twitter`,
  canonical alternates, or route metadata outside the root layout.
- `rg --files src/app | rg 'robots|sitemap|manifest|icon|opengraph|twitter'`
  returned only `src/app/favicon.ico`.
- No JSON-LD or `schema.org` structured data was found for artwork, products,
  breadcrumbs, or articles.

Impact: every public route inherits incorrect scaffold metadata, and crawlers
lack canonical URLs, social preview data, a sitemap, robots directives, and
structured discovery signals for artwork/product relationships.

Candidate follow-up: add owner-approved root metadata, route-specific
`generateMetadata` for public detail/list routes, `app/sitemap.ts`,
`app/robots.ts`, and structured data for artwork detail, product detail,
article/blog detail, and breadcrumbs.

### A010-F03: Home hero preloads multiple large carousel images at quality 100

Severity: Medium

Evidence:

- `src/components/modules/hero/Hero.tsx` renders four carousel items at once:
  `FilterableArtworks`, `ComingSoonSlide`, `LargeScaleWorks`, and
  `FamilyFavourites`.
- Each active slide image sets `priority={true}` and `quality={100}` in the
  active slide components.
- `FilterableArtworks` and `LargeScaleWorks` use `fill` images without an
  explicit `sizes` value, so the browser can over-select image candidates.

Impact: the home route risks preloading non-visible carousel images and using
unnecessarily large Cloudinary/Next image payloads. This can delay LCP and
consume bandwidth before users interact with the carousel.

Candidate follow-up: mark only the initially visible hero image as priority,
lazy-load non-visible slides, add accurate `sizes` for every `fill` image, and
lower quality or move Cloudinary delivery transformations into the central asset
policy from A-009.

### A010-F04: Detail image behavior creates extra image payload and sizing risk

Severity: Medium

Evidence:

- `src/app/shop/products/[productHandle]/page.tsx` uses `fill` images without
  `sizes` for the primary product image and book artwork thumbnails.
- `src/app/shop/products/page.tsx` also uses a `fill` priority banner image
  without `sizes`.
- `src/components/modules/MagnifierImage.tsx` preloads the source artwork again
  through `new window.Image(width * magnificationLevel, height *
  magnificationLevel)` on mount, while the visible image is also rendered via
  `next/image`.

Impact: product and artwork detail pages can fetch larger-than-needed image
candidates. Artwork detail pages also create a second client-side image request
for the magnifier, even before the user hovers, which is expensive for archival
high-resolution images.

Candidate follow-up: add accurate `sizes` to product/detail `fill` images,
defer magnifier high-resolution preload until pointer/focus intent, and document
a Cloudinary/Next size strategy for artwork detail versus zoom views.

### A010-F05: Public navigation/search controls still have keyboard and naming gaps

Severity: High

Evidence:

- `src/components/elements/inputs/Searchbar.tsx` renders the search submit icon
  as a clickable `<div onClick={handleSearch}>`; it is not keyboard focusable
  and has no accessible name.
- `src/components/modules/search/SearchDrawer.tsx` passes a bare `<Search />`
  icon as `DrawerTrigger asChild`; it is not a labelled button.
- `src/components/modules/navigation/mobileNavDrawer/MobileNavDrawer.tsx` uses
  bare `<Menu />` and `<X />` icons as drawer trigger/close controls.
- `WatchlistButton` and `FavouritesButton` wrap unauthenticated actions in
  clickable `<div>` elements around a submit button, which creates ambiguous
  interaction semantics.

Impact: keyboard and assistive-technology users can miss or be unable to
activate core public discovery and account-intent controls. `npm run lint`
passes, so this currently needs targeted component tests or manual accessibility
checks.

Candidate follow-up: convert icon triggers and clickable wrappers to real
`button` elements with stable labels, preserve drawer semantics through Radix
`asChild`, and add focused tests for desktop search, mobile search/nav drawer,
and unauthenticated artwork actions.

### A010-F06: Public pages produce nested landmarks and noisy heading hierarchy

Severity: Medium

Evidence:

- `src/app/layout.tsx` wraps all children in a root `<main>`.
- Public page/view components also render `<main>`, including
  `src/app/blog/[slug]/page.tsx`, `src/app/shop/products/page.tsx`,
  `src/app/shop/products/[productHandle]/page.tsx`, `src/app/project/aims/page.tsx`,
  `src/app/project/film/page.tsx`, `src/components/views/ArticleView.tsx`, and
  `src/components/sections/AccountSettings.tsx`.
- Heading search shows many presentational `h1` elements in repeated UI pieces,
  including logo text, section cards, sidebar groups, carousel slides, and
  account/menu labels.

Impact: public pages can expose multiple main landmarks and multiple unrelated
top-level headings, making page structure harder for screen-reader navigation
and SEO interpretation.

Candidate follow-up: keep the root layout as the single page-level `<main>` or
move page-level landmarks out of the root; then normalize repeated card/logo/nav
headings to paragraphs/spans or lower-level headings tied to visible sections.

### A010-F07: Artwork-to-shop discovery depends on client-side product fetches

Severity: Medium

Evidence:

- `src/components/modules/cards/ArtworkShopSection.tsx` is a client component
  that fetches linked Shopify products in `useEffect` via
  `/api/v2/public/shop/products/:productId`.
- The SSR output can show availability badges from `artwork.shopifyProducts`,
  but actual product links and prices are rendered only after client fetches
  complete.
- Product detail pages do server-render links back to linked artwork when
  Shopify metadata includes `mongodbArtworkId`, but the artwork detail to
  product direction is not equally discoverable in initial HTML.

Impact: the archive-to-commerce relationship is weaker for crawlers and users on
slow networks, and artwork detail pages incur extra client/API waterfalls before
showing shop links.

Candidate follow-up: resolve linked product summaries server-side in the artwork
detail loader/service and render stable product links in initial HTML, with
client enhancement reserved for live availability or richer commerce state.
